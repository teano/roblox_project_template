# Product Requirements

## Product Outcome

Переиспользуемый production-модуль должен на сервере собирать числовую статистику игрока одновременно за всё время, за текущую игровую сессию, за каждое посещение плейса и за определяемые проектом интервалы. Накопленные данные должны быть пригодны для аналитики, интерфейсов и проектных систем, которым требуется проверить выполнение действия заданное число раз за определённый период.

Модули-источники не должны знать, какие показатели из их поведения собираются. Отдельные интеграционные контроллеры преобразуют подтверждённые доменные факты в операции статистики. Модуль статистики отвечает за безопасное накопление, снимки, историю и чтение данных, но не за достижения, награды или интерпретацию показателей.

## Target Audience

- Разработчики проектов на основе шаблона, которым нужен готовый серверный контракт сбора произвольных числовых показателей.
- Игроки, чья статистика должна согласованно продолжаться между плейсами одного Experience и не теряться при штатном сохранении.
- Проектные серверные и клиентские контроллеры, которым нужны безопасные способы отправки фактов и чтения разрешённой проекции без изменения базового модуля.

## Core Gameplay Loop

1. Сервер загружает профиль игрока, продолжает глобальный снимок и определяет по `TeleportModule`, начинается новая игровая сессия или продолжается подтверждённая сессия между плейсами.
2. Сервер продолжает либо создаёт сессионный снимок и создаёт новый снимок посещения текущего плейса.
3. Интеграционные контроллеры наблюдают подтверждённые изменения предметных модулей и передают серверу операции `Set`, `Inc`, `Dec`, `Min` или `Max`.
4. Одна операция последовательно и атомарно применяется ко всем активным снимкам, чьи зафиксированные правила разрешают этот показатель.
5. Серверные потребители читают текущие или закрытые снимки и подписываются на локальные изменения; клиент может запрашивать только разрешённую проекцию своих текущих глобального, сессионного и плейсового снимков.
6. При уходе игрока текущие сессионный и плейсовый снимки закрываются. При подтверждённом телепорте целевой сервер продолжает тот же сессионный снимок и создаёт новый плейсовый снимок; при следующем внешнем входе начинается новая сессия.

## Release Target

Первая версия предназначена для production-использования в переиспользуемом Roblox-шаблоне. Она должна использовать существующие границы инициализации, сохранения, коммуникации, игроков и телепортации, работать в пределах DataStore и сетевых лимитов Roblox и включать проверяемую интеграцию с Wallet.

## Scope

### In Scope

- Глобальный, сессионный и плейсовый типы снимков.
- Пользовательские типы снимков, объявляемые конкретным проектом.
- Не более одного активного снимка каждого типа для одного игрока.
- Запуск нового, продолжение сохранённого, явное сохранение, закрытие и чтение снимков.
- Операции `Set`, `Inc`, `Dec`, `Min` и `Max` над числовыми показателями.
- Настраиваемая фильтрация показателей по типу снимка; при отсутствии правила показатель записывается во все активные снимки.
- Настраиваемая ограниченная история закрытых снимков.
- Системные и расширяемые пользовательские метаданные снимков.
- Серверные события изменения и стабильные server-side read API.
- Ограниченные read-only запросы клиента для собственных текущих глобального, сессионного и плейсового снимков.
- Получение подтверждённых клиентских фактов через проектную коммуникационную границу и server-side контроллер.
- Сохранение Statistics как серверного провайдера существующего глобального профиля.
- Продолжение сессионного снимка через подтверждённый session ID существующего `TeleportModule`.
- Тестовая интеграция Wallet, считающая суммарно полученную валюту после завершения начальной загрузки.

### Out of Scope

- Выдача достижений, наград, валюты или прогресса по накопленной статистике.
- Решение о том, какой показатель достаточно доверен для награды; это ответственность конкретного проекта.
- Аналитическая отправка данных во внешние сервисы и построение отчётов.
- Владение предметной бизнес-логикой модулей-источников.
- Прямое изменение статистики Roblox-клиентом.
- Клиентское чтение закрытой истории, пользовательских типов или непубличных показателей.
- Передача авторитетных значений статистики через `TeleportData` или MemoryStore.
- Абсолютная гарантия сохранения изменений при аварийном завершении Roblox-сервера до очередного успешного autosave.
- Автоматическая политика жизненного цикла пользовательских снимков; её задаёт конкретный проект.

## Functional Requirements

- `PRD-REQ-001`: Модуль должен поддерживать встроенные типы `Global`, `Session` и `Place` и позволять проекту объявлять дополнительные стабильные типы без изменения базовой логики снимков.
- `PRD-REQ-002`: Для одного игрока одновременно может существовать не более одного активного снимка каждого типа. Повторный запуск или продолжение уже активного типа должно завершаться явным отказом без изменения состояния.
- `PRD-REQ-003`: Глобальный снимок должен создаваться при первом появлении Statistics provider, затем продолжаться при каждом последующем входе и не закрываться обычными операциями жизненного цикла игрока.
- `PRD-REQ-004`: Сессионный снимок должен охватывать один внешний вход игрока в Experience и все подтверждённые переходы между плейсами этой сессии.
- `PRD-REQ-005`: Для каждого посещения плейса должен создаваться новый плейсовый снимок, включая повторное посещение того же плейса в одной сессии.
- `PRD-REQ-006`: Модуль должен поддерживать операции `Set`, `Inc`, `Dec`, `Min` и `Max` с reference-семантикой: отсутствующее значение считается равным `0`, отрицательный операнд нормализуется в `0`, а результат `Dec` не становится отрицательным.
- `PRD-REQ-007`: Принятая операция должна применяться ко всем активным снимкам игрока, которые разрешают соответствующий `StatisticId`.
- `PRD-REQ-008`: Для типа снимка должны поддерживаться режимы «разрешить всё, кроме списка» и «разрешить только список». Если правило для типа отсутствует, действует «разрешить всё» без исключений.
- `PRD-REQ-009`: Закрытые снимки должны храниться по типам в порядке создания с настраиваемым конечным retention-лимитом. Значение `0` означает не хранить закрытую историю этого типа; активный снимок не удаляется retention-очисткой.
- `PRD-REQ-010`: Server-side API должен позволять получить безопасную копию активного снимка, снимок по типу и ID, последний снимок, заданное число последних снимков и все сохранённые снимки заданного типа в пределах настроенного лимита.
- `PRD-REQ-011`: Server-side API должен позволять получить конкретное значение из текущего или указанного снимка; отсутствующий `StatisticId` возвращает числовое значение `0` без создания записи.
- `PRD-REQ-012`: Авторитетные снимки, значения, история и операции изменения должны существовать только на сервере.
- `PRD-REQ-013`: Roblox-клиент не должен указывать авторитетный итог, произвольную операцию или произвольный `StatisticId`. Клиент может отправить только объявленное проектом событие, которое server-side контроллер проверяет и преобразует в заранее определённую операцию.
- `PRD-REQ-014`: Модуль должен предоставлять явные операции `StartNewSnapshot`, `ContinueSnapshot`, `CloseSnapshot`, `SaveSnapshot` и соответствующие структурированные результаты успеха или отказа.
- `PRD-REQ-015`: Политика автоматического запуска, продолжения и закрытия пользовательских типов определяется проектным контроллером; базовый модуль не должен угадывать её по имени типа.
- `PRD-REQ-016`: Повторное закрытие уже закрытого или отсутствующего снимка не должно создавать вторую историю, повторно применять retention или повреждать данные; результат должен однозначно сообщать, что активного снимка не было.
- `PRD-REQ-017`: Сервер должен публиковать локальное событийное уведомление после успешного атомарного изменения снимков и после изменения набора активных снимков.
- `PRD-REQ-018`: Событийные уведомления являются дополнением к read API; потребитель должен иметь возможность восстановить текущее состояние повторным чтением без воспроизведения всей истории событий.
- `PRD-REQ-019`: Возвращаемые снимки, списки, значения и метаданные не должны предоставлять вызывающему коду изменяемую ссылку на внутреннее состояние.
- `PRD-REQ-020`: Идентификаторы снимков должны монотонно увеличиваться в пределах типа и не переиспользоваться после retention-удаления старых снимков.
- `PRD-REQ-021`: Входной операнд и вычисленный результат должны быть конечными числами Roblox. Неконечный вход или результат, включая overflow в бесконечность, отклоняет всю операцию и не превращается в `0`.
- `PRD-REQ-022`: Успешная операция, которая не меняет ни одного разрешённого снимка, не должна создавать ложное уведомление об изменении или лишнее dirty-состояние.
- `PRD-REQ-023`: Правила фильтрации, применяемые снимком, должны фиксироваться при его создании; изменение конфигурации не должно задним числом менять смысл уже созданного снимка.
- `PRD-REQ-024`: Продолжение снимка должно восстанавливать его сохранённые значения, метаданные и зафиксированные правила, а не создавать новый снимок с тем же ID.
- `PRD-REQ-025`: Модуль должен отклонять неизвестный тип, неизвестную операцию, некорректный `StatisticId`, некорректные метаданные и недопустимый переход жизненного цикла до частичной мутации.
- `PRD-REQ-026`: Интеграционные контроллеры должны быть отдельными от модулей-источников и модуля статистики. Предметный модуль не должен импортировать Statistics или знать, какие его изменения отслеживаются.
- `PRD-REQ-027`: Прямой вызов Statistics из предметного клиентского или серверного кода допускается только как явно одобренное проектом исключение, когда отдельный интеграционный контроллер объективно невозможен.
- `PRD-REQ-028`: При уходе игрока с текущего сервера плейсовый снимок должен закрываться. Если игрок фактически прибыл после подтверждённого внутреннего телепорта, целевой сервер должен создать новый плейсовый снимок независимо от предыдущего PlaceId.
- `PRD-REQ-029`: При уходе игрока с текущего сервера сессионный снимок должен закрываться в сохраняемом состоянии. Только подтверждённое продолжение того же Teleport session ID может снова активировать этот снимок на целевом сервере; внешний или недоверенный вход создаёт новый сессионный снимок.
- `PRD-REQ-030`: Начальный баланс Wallet, применённый при создании или загрузке профиля, не должен учитываться как полученная валюта.
- `PRD-REQ-031`: Тестовая Wallet-интеграция должна увеличивать отдельный показатель суммарно полученной валюты для каждой поддерживаемой валюты только на положительную дельту успешного runtime-изменения; траты, отказавшие операции и изменение без фактической дельты не учитываются.
- `PRD-REQ-032`: Каждое успешное изменение Statistics должно немедленно менять server runtime и помечать Statistics provider изменённым, но не выполнять отдельную DataStore-запись на каждую операцию.
- `PRD-REQ-033`: `CloseSnapshot` должен атомарно обновить runtime, историю, retention и dirty-состояние, но сам по себе не обязан вызывать `ForceSave`. Штатный выход игрока, teleport handoff и shutdown сохраняются существующим глобальным save-контуром; `SaveSnapshot` направляет ограниченный и объединяемый запрос тому же контуру.
- `PRD-REQ-034`: Модуль не должен проверять условия достижений, выбирать награду или выдавать её.
- `PRD-REQ-035`: Проект-потребитель самостоятельно выбирает показатели и снимки для аналитики, достижений и наград и несёт ответственность за использование только достаточно доверенных источников.
- `PRD-REQ-036`: Каждый снимок должен иметь явные системные поля как минимум `SnapshotId`, `SnapshotType`, время начала, необязательное время закрытия и состояние жизненного цикла; плейсовый снимок дополнительно хранит `PlaceId`, а сессионный — внутренний ключ продолжения.
- `PRD-REQ-037`: Проект может передать при создании снимка дополнительную таблицу `Metadata`, не изменяя базовый модуль.
- `PRD-REQ-038`: Пользовательские метаданные должны быть DataStore-safe: допустимы строки UTF-8, boolean, конечные числа, плотные массивы и словари со строковыми ключами в пределах настроенных глубины, числа узлов и размера.
- `PRD-REQ-039`: Метаданные валидируются и копируются до создания снимка, не могут переопределять системные поля и остаются неизменяемыми в течение жизни снимка.
- `PRD-REQ-040`: Для ранее сохранённого снимка без `Metadata` должна использоваться пустая таблица; расширение метаданных не должно требовать реконструкции исторических значений.
- `PRD-REQ-041`: Statistics должен использовать только server-owned Teleport session ID из готового `TeleportModule` как ключ корреляции. Авторитетные значения снимка не должны передаваться через `TeleportData`.
- `PRD-REQ-042`: Продолжение сессионного снимка на целевом сервере разрешается только когда `TeleportModule` классифицировал вход как подтверждённый `Teleported`, а загруженный профиль содержит закрытый сессионный снимок с тем же session ID. При отсутствии точного совпадения сервер начинает новую сессию и не сливает данные разных сессий.
- `PRD-REQ-043`: Принятие `TeleportAsync` не должно закрывать снимки и не является доказательством продолжения. Пока игрок остаётся на исходном сервере после синхронного или позднего отказа, текущие снимки и их значения должны оставаться активными и неизменными.
- `PRD-REQ-044`: Нормальный межплейсовый переход должен сохранять закрытые на источнике Statistics вместе с глобальным профилем и освобождать session lock; целевой сервер использует существующее ограниченное ожидание lock handoff и загружает только подтверждённое сохранённое состояние.
- `PRD-REQ-045`: Подтверждённые доменные факты для одного игрока должны приниматься Statistics ровно один раз и в исходном порядке. Все факты, принятые до начала штатного закрытия профиля, должны быть применены до финального capture/save.
- `PRD-REQ-046`: Интеграция не должна полагаться на best-effort асинхронное уведомление, которое может выполниться после закрытия провайдеров. Контракт источника и контроллера должен предоставлять наблюдаемое подтверждение принятия факта либо упорядоченный drain перед закрытием.
- `PRD-REQ-047`: Если доменный факт содержит устойчивый идентификатор, например Wallet `TransactionId`, повторная доставка того же идентификатора не должна повторно изменять статистику.
- `PRD-REQ-048`: Одна операция Statistics должна быть атомарной между всеми подходящими активными снимками: сначала рассчитываются и проверяются все результаты и лимиты, затем применяются все изменения. Ошибка одного снимка оставляет каждый снимок неизменным и не публикует событие успеха.
- `PRD-REQ-049`: Клиентский read API должен возвращать только собственную разрешённую проекцию одного текущего встроенного снимка или одного разрешённого значения. По умолчанию ни один `StatisticId` и ни одно пользовательское metadata-поле не являются публичными; публичность задаётся явным allowlist проекта.
- `PRD-REQ-050`: Клиентский read API должен использовать общий bounded request-контур, общую per-player rate policy и лимит ответа. Превышение лимита возвращает явный отказ без усечения, частичной выдачи или изменения серверного состояния.
- `PRD-REQ-051`: Конфигурация должна задавать конечные пределы числа типов, закрытых снимков, показателей в одном снимке, длины идентификаторов, размера одного снимка, метаданных и всего Statistics provider. При превышении операция отклоняется до мутации; данные не обнуляются и не удаляются вне явной retention-политики.
- `PRD-REQ-052`: Statistics должен быть версионированным серверным save provider существующего глобального профиля. Отсутствующий provider создаётся пустым, начинает глобальный отсчёт с установки фичи и не реконструирует прошлое; некорректный сохранённый provider должен завершать загрузку fail-closed, а не заменяться нулями.

## Quality Requirements

- `PRD-NFR-001`: Модуль должен сохранять серверный авторитет над всеми значениями и жизненным циклом снимков.
- `PRD-NFR-002`: Предметные модули должны оставаться независимыми от Statistics; интеграция выполняется через явную композицию отдельных контроллеров.
- `PRD-NFR-003`: Все возвращаемые данные должны быть изолированными копиями, а внутренние таблицы не должны утекать потребителям.
- `PRD-NFR-004`: Одна подтверждённая доменная операция не должна учитываться дважды ни в одном снимке, включая повторную доставку одного transaction ID.
- `PRD-NFR-005`: Ошибка клиента, некорректный запрос или неподдерживаемое событие не должны изменять статистику другого или текущего игрока.
- `PRD-NFR-006`: Жизненный цикл и API должны быть детерминированными и возвращать структурированный отказ вместо частично применённого состояния.
- `PRD-NFR-007`: Система должна работать с одним числовым типом Luau без округления или преобразования к отдельным integer/float-хранилищам.
- `PRD-NFR-008`: Отсутствующее значение логически равно `0`, но чтение отсутствующего значения не должно раздувать сохранённые данные.
- `PRD-NFR-009`: Конфигурация фильтрации, retention, публичной проекции и лимитов должна валидироваться fail-closed до обработки игроков.
- `PRD-NFR-010`: Межплейсовая сессия не должна зависеть от продолжения работы исходного сервера после сохранения и освобождения lock.
- `PRD-NFR-011`: Неконечные числа, циклы, metatable, смешанные или разреженные таблицы и небезопасные строки не должны попадать в DataStore или сетевой ответ.
- `PRD-NFR-012`: DataStore-записи должны выполняться существующей autosave/close/shutdown политикой, объединять параллельные запросы и не масштабироваться линейно с числом статистических операций или быстро закрываемых пользовательских снимков.
- `PRD-NFR-013`: Шаблон не должен делать вид, что клиентский факт автоматически безопасен для награды; доверие и интерпретация остаются явным решением проекта.
- `PRD-NFR-014`: Пользовательские метаданные должны оставаться расширяемыми без неограниченного роста, изменения системных полей или нарушения обратной совместимости старых снимков.
- `PRD-NFR-015`: Нормальный выход, подтверждённый teleport handoff и shutdown не должны терять уже принятые Statistics-операции; финальный save выполняется после drain и до освобождения профиля.
- `PRD-NFR-016`: Аварийное завершение Roblox-сервера может потерять изменения после последнего успешного autosave; интервал autosave и наблюдаемая диагностика являются принятой границей платформенной гарантии.
- `PRD-NFR-017`: Все коллекции истории и runtime-очереди должны иметь конечные пределы; переполнение не должно приводить к silent drop авторитетных фактов или сбросу накопленных значений.
- `PRD-NFR-018`: Client projection не должна раскрывать непубличные показатели, внутренний session ID, служебные поля дедупликации или непубличные метаданные.
- `PRD-NFR-019`: Отклонённые операции, дубликаты, переполнение, retention-удаления, ошибки handoff и persistence failures должны давать ограниченные структурированные диагностические записи без спама и без содержимого защищённых данных.
- `PRD-NFR-020`: Публичные операции жизненного цикла и очистка игрока должны быть безопасны при повторном вызове и не создавать дубликаты закрытых снимков.
- `PRD-NFR-021`: Сохранённый Statistics provider вместе с остальными провайдерами должен оставаться ниже существующего soft limit глобального профиля; oversized-состояние не должно перезаписывать последнюю корректную DataStore-версию.
- `PRD-NFR-022`: Детерминированные тесты должны покрывать операции, фильтры, retention, лимиты, атомарность, дедупликацию, close/drain, save rollback, клиентскую безопасность и teleport continuity; опубликованный межплейсовый E2E переиспользует доказательства TeleportModule и save-lock handoff.

## Acceptance Criteria

- `PRD-AC-001`: При первом входе игрок получает один активный глобальный, один сессионный и один плейсовый снимок; второй активный снимок того же типа создать нельзя.
- `PRD-AC-002`: Повторный внешний вход продолжает глобальный снимок, создаёт новую сессию и новое посещение плейса.
- `PRD-AC-003`: Пользовательский контроллер может создать, прочитать, закрыть и продолжить один сохранённый пользовательский снимок без изменения базового модуля.
- `PRD-AC-004`: Операции `Set`, `Inc`, `Dec`, `Min` и `Max` дают reference-результаты от исходного `0`, включая отсутствие отрицательного результата `Dec`.
- `PRD-AC-005`: Одна операция обновляет все разрешившие её активные снимки и не меняет снимок, фильтр которого исключает этот `StatisticId`.
- `PRD-AC-006`: При отсутствии правила фильтрации новый показатель записывается во все активные снимки; правило allow-only и правило allow-all-except дают противоположные ожидаемые выборки.
- `PRD-AC-007`: Закрытие снимков сверх retention удаляет только самые старые закрытые снимки этого типа, не удаляет активный снимок и не переиспользует их ID.
- `PRD-AC-008`: Server-side чтение снимка и метаданных возвращает копию; изменение возвращённой таблицы не меняет сохранённое или runtime-состояние.
- `PRD-AC-009`: Клиент не может вызвать generic Statistics mutation или выбрать произвольный `StatisticId` через сетевой payload.
- `PRD-AC-010`: Валидное проектное клиентское событие после server-side проверки преобразуется контроллером в фиксированную операцию; неизвестное, невалидное или превысившее rate policy событие не меняет снимки.
- `PRD-AC-011`: Серверное событие изменения публикуется только после успешного применения и позволяет потребителю перечитать согласованный текущий снимок.
- `PRD-AC-012`: Повторный `CloseSnapshot` не создаёт вторую запись истории и возвращает определённый результат `NotActive` либо эквивалентный безопасный no-op.
- `PRD-AC-013`: Продолжение существующего снимка восстанавливает его значения, системные поля, метаданные и зафиксированный фильтр.
- `PRD-AC-014`: Неконечный вход, overflow-результат, неизвестная операция или недопустимый переход отклоняются без изменения любого снимка.
- `PRD-AC-015`: Отсутствующий показатель читается как `0`, но после одного только чтения не появляется в сериализованном снимке.
- `PRD-AC-016`: Подтверждённый переход между двумя плейсами одного Experience сохраняет один session ID и один сессионный `SnapshotId`.
- `PRD-AC-017`: На том же переходе исходный плейсовый снимок закрывается, а целевой сервер создаёт плейсовый снимок с новым ID и своим `PlaceId`.
- `PRD-AC-018`: Синхронный или поздний `TeleportInitFailed`, пока игрок остаётся на исходном сервере, не закрывает и не заменяет текущие снимки.
- `PRD-AC-019`: Вход с недоверенным, отсутствующим или не совпавшим с сохранённым Teleport session ID не продолжает старый сессионный снимок и начинает новую сессию.
- `PRD-AC-020`: Начальные `Coins` и `Gems`, применённые Wallet при первом `Run`, не увеличивают показатели полученной валюты.
- `PRD-AC-021`: Успешное добавление валюты увеличивает соответствующие показатели во всех разрешённых активных снимках на положительную дельту; трата и отказавшее добавление их не меняют.
- `PRD-AC-022`: Серия статистических операций помечает provider dirty, но не создаёт одну DataStore-запись на каждую операцию.
- `PRD-AC-023`: Быстрое закрытие нескольких пользовательских снимков обновляет runtime и историю, а persistence-запросы объединяются существующим save-контуром; штатный уход сохраняет итоговое состояние перед release lock.
- `PRD-AC-024`: Базовый Statistics API не содержит метода выдачи достижения или награды, а тестовый reward-потребитель может только читать или наблюдать данные извне модуля.
- `PRD-AC-025`: Снимок сохраняет обязательные системные поля, а плейсовый снимок дополнительно сохраняет правильный `PlaceId`.
- `PRD-AC-026`: Валидные пользовательские `RunId`, `EventId`, `Difficulty` и `MapId` могут быть записаны в `Metadata` без изменения базового schema-кода.
- `PRD-AC-027`: После создания вызывающий код не может изменить `Metadata` через исходную или возвращённую таблицу; попытка передать слишком глубокие, oversized или DataStore-unsafe метаданные отклоняет создание.
- `PRD-AC-028`: Старый снимок без поля `Metadata` загружается с пустой таблицей и сохраняет прежние значения.
- `PRD-AC-029`: Три подтверждённых последовательных посещения плейсов продолжают один сессионный снимок, создают три разных плейсовых снимка и не передают значения Statistics в teleport envelope.
- `PRD-AC-030`: При нормальном teleport handoff целевой load ожидает release исходного session lock, после чего видит все факты, принятые источником до close; если ожидание исчерпано, загрузка завершается fail-closed без создания пустого профиля.
- `PRD-AC-031`: Wallet-факт, принятый непосредственно перед `PlayerRemoving`, обрабатывается drain-механизмом и присутствует в финальном сохранённом сессионном, плейсовом и глобальном состоянии.
- `PRD-AC-032`: Повторная доставка одного Wallet `TransactionId` изменяет каждый подходящий снимок ровно один раз.
- `PRD-AC-033`: Если один из трёх подходящих снимков превысил бы лимит или получил невалидный результат, значения всех трёх снимков остаются прежними и событие успеха не публикуется.
- `PRD-AC-034`: Клиентский запрос глобальной, сессионной или плейсовой проекции возвращает только allowlisted показатели и метаданные текущего игрока; непубличные и служебные поля отсутствуют.
- `PRD-AC-035`: Запрос закрытой истории, пользовательского типа, другого игрока или oversized-ответа завершается явным отказом без частичной выдачи; частые запросы ограничиваются общей per-player policy.
- `PRD-AC-036`: Попытка создать новый `StatisticId` сверх лимита отклоняется без изменения существующих значений; обновление существующего ID остаётся допустимым, пока итоговый снимок и provider проходят лимиты.
- `PRD-AC-037`: Oversized или повреждённый Statistics provider не перезаписывает последнюю корректную DataStore-версию и не заменяется пустыми значениями при следующей загрузке.
- `PRD-AC-038`: Профиль, созданный до появления Statistics provider, получает пустую статистику и начинает глобальный отсчёт с первого успешного запуска новой версии без выдуманных исторических значений.
- `PRD-AC-039`: Структурированные diagnostics для invalid input, duplicate, overflow, retention и persistence failure ограничены по частоте и не содержат полных снимков, session ID или пользовательских метаданных.

## Assumptions

- Репозиторий является переиспользуемым template-репозиторием и поставляет Statistics как production-компонент.
- Существующие `PlayersModule`, `TeleportModule`, global save provider pipeline, session locking, autosave и communication boundary остаются авторитетными интеграционными границами.
- `TeleportModule` уже проверяет происхождение прибытия и предоставляет server-owned session ID; Statistics не дублирует этот протокол.
- Сессионный снимок может быть закрыт на исходном сервере и снова активирован на целевом сервере с тем же ID; это считается продолжением одного логического снимка, а не двумя снимками истории.
- Клиентские события по своей природе недоверенны. Проектный server-side контроллер определяет, достаточно ли их проверки для выбранного применения.
- Общая save-политика с autosave и финальным save на штатном close была выбрана вместо записи каждого изменения.
- Точные числовые значения application-level лимитов и retention defaults будут выбраны технической спецификацией так, чтобы полный профиль оставался ниже существующего DataStore soft limit.

## Risks

- Жёсткое завершение сервера Roblox может потерять изменения после последнего успешного autosave; абсолютная exactly-once durability без записи каждой операции платформой не гарантируется.
- Чисто клиентский факт может быть подделан. Server-side mapping и rate limiting ограничивают поверхность атаки, но не превращают неподтверждаемую телеметрию в авторитетное доказательство для награды.
- Некорректные или чрезмерно широкие retention и public-projection настройки могут увеличить DataStore или сетевой размер; configuration validation и конечные лимиты должны завершаться fail-closed.
- Асинхронный доменный Signal без контракта принятия/drain может потерять последнее изменение при close; техническая спецификация должна выбрать упорядоченную интеграцию, а не полагаться на планирование `task.spawn`.
- Истощение session-lock handoff window на целевом сервере приводит к fail-closed load и повторному входу игрока, но не к созданию пустого или объединённого профиля.
- Замена overflow-результата на `0`, как в Unity-референсе, могла бы уничтожить lifetime-статистику; Roblox-версия намеренно отклоняет такую операцию целиком.
- Неограниченное добавление `StatisticId`, типов или метаданных может переполнить профиль даже при малом retention; все измерения должны ограничиваться совместно.
