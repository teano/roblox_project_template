# Миграции в шаблон

Здесь хранится происхождение систем, принятых в шаблон из других проектов:
когда, откуда и что перенесено, как адаптировано и что требуется существующим
играм. Это журнал переносов, а не описание текущего поведения систем.

## Как вести журнал

- Один самостоятельный перенос — один файл `MIG-####-<краткое-имя>.md`.
  Следующий номер берётся из этой таблицы. Обычное исправление системы
  не создаёт новую миграцию; дополнение ещё не законченного переноса остаётся
  в его записи.
- В записи нужны происхождение и точные ревизии, состав по подсистемам,
  существенная адаптация, ссылки на принятые решения, действия для существующих
  игр, результат проверки и его ограничения. Большие перечни файлов, копии
  исходных инструкций, журналов и контрольных сумм сюда не переносятся.
- Ссылки на исходные решения и материалы закрепляются полным коммитом,
  а не изменяемой веткой. Если исходник не зафиксирован, запись прямо говорит
  об этом и не объявляет такую ревизию воспроизводимой.
- Целевой коммит означает коммит шаблона, содержащий перенос. Пока он не
  создан, указываются рабочая ветка и отсутствие фиксации. После фиксации
  коммит вписывается в запись следующим документальным изменением; документ
  не должен содержать хеш самого себя.
- Проверка относится только к указанной редакции и среде. Позднее изменение
  кода не получает автоматически результаты предыдущего запуска.

Текущее устройство описывают системные руководства; причины устройства —
[ADR шаблона](../adr/template/README.md). Связанные ADR содержат служебную
ссылку на миграцию, а запись миграции ссылается на ADR и исходные материалы.
Историческое решение не становится действующим только из-за переноса ссылки.

Обновление производной игры выполняется по [штатной процедуре](../TemplateWorkflow.md).
Запись миграции дополняет её конкретными шагами и не заменяет команду обновления.
